# 端到端加密与消失消息

单独定义设备密钥、参与者信任和消息留存的承诺。服务端可见的元数据和参与设备的能力要能审查。

阶段验收目标：先验证端到端加密的一对一私聊及一种明确的自动消失规则，再评审加密群。

本页维护各子专题的设计与执行状态。跨专题顺序见[整体规划](../planning/project-plan.md)，近期优先级见[当前状态](../status/current.md)。

<a id="lock-01"></a>

## LOCK-01 协议选型与加密私聊

- 阶段与状态：P3。规划，待开始。
- 范围：比较成熟方案的客户端支持、许可、设备确认、轮换和恢复。明确会话类型、内容与元数据可见面。
- 依赖与基础：P0 先提供下列设计输入，供首批合同评审。P3 评估 Matrix 等候选的适用性，与 [AUTH-04](identity.md#auth-04) 约定设备信任，并用隔离试验验证。
- 验收：两设备在明确身份信任下收发。验证服务端、未受信任设备及已撤销设备各自可见的内容，覆盖撤销后的新消息和密钥。换机和恢复按合同验证。

<a id="p1-privacy-boundary"></a>

### P1 普通会话与后续加密的设计边界

| 边界 | P1 内测约定 | 后续设计输入 |
| --- | --- | --- |
| 传输、存储与会话类型 | 内测远程连接使用 HTTPS。普通私聊和群聊的正文由服务端处理并持久化，拥有数据库或备份访问权的人员可接触正文。界面和内测说明明确这一点 | 会话和 API 能表达不同安全类型，客户端据实显示。加密会话的正文、元数据与密钥分别定义可见范围，禁止静默降级 |
| 账号、会话与设备 | 本地登录确定实例内账号，服务端按会话和成员关系判断访问权限 | Radish 登录同样映射为实例内账号。设备确认、密钥分发和历史解密权限单独定义。登录、重置密码或恢复账号本身不会赋予加密历史解密权限。与 [AUTH-04](identity.md#auth-04) 联合评审 |
| 撤权、同步与历史 | 成员撤权后停止该账号从服务端取得该会话内容。客户端清理已打开会话。群历史按本次加入边界授权。同步信号只提示检查更新，正文和历史由授权接口返回。先前取得的副本可能继续存在 | 区分账号退出、成员移除和设备撤销。加密方案定义撤销后新消息、未来密钥和此前已取得数据各自的边界 |
| 日志、备份与消失语义 | 日志和诊断字段按用途收敛，排除消息正文、凭据和会话令牌。备份按普通会话数据限制访问，明确存放与恢复方式，恢复后要求重新登录 | 消失时间、离线补拉、通知和备份清理由 [LOCK-02](#lock-02) 定义。产品说明列明可验证的覆盖范围和接收方保留副本的边界 |

上述边界已纳入 [BASE-02](foundation.md#base-02) 首批合同，由 [MSG-01](messaging.md#msg-01)、[MSG-02](messaging.md#msg-02)、[WEB-01](clients.md#web-01) 和 [OPS-01](deployment.md#ops-01) 联合验收。加密协议、设备密钥与消失消息的具体合同随各自子专题评审和实施。

<a id="lock-02"></a>

## LOCK-02 限时消息与阅后消失

- 阶段与状态：P3。规划，待开始。
- 范围：定义发送后或读后起算、未读上限、离线补拉、备份、设备时钟、通知、引用和转发。首期先选定一种适用会话与语义。
- 依赖与基础：依赖 MSG-02 与 LOCK-01 的会话契约。需明确清理覆盖的设备和可保存副本。
- 验收：计时及失效语义在多设备、离线和恢复场景可复现。产品文案与实际覆盖一致。

<a id="lock-03"></a>

## LOCK-03 加密群与高级恢复

- 阶段与状态：后续。规划，待开始。
- 范围：评审群成员变动、设备撤销、历史共享、密钥备份及加密会话的能力限制。
- 依赖与基础：先取得 LOCK-01/02 的实践证据。
- 验收：加入、退出、失窃和数据恢复均有独立验收，按选定方案给出隐私与可用性取舍。
